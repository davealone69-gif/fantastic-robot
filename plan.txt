// Rust Host Conceptual Implementation: Native shadow-nudge task
async fn spawn_shadow_nudge(
    mut rx_bytes: tokio::sync::watch::Receiver<usize>,
    cancel_token: CancellationToken
) {
    let mut last_activity = std::time::Instant::now();
    let timeout_duration = std::time::Duration::from_secs(600); // 10 minutes

    loop {
        tokio::select! {
            _ = cancel_token.cancelled() => break,
            Ok(_) = rx_bytes.changed() => {
                last_activity = std::time::Instant::now();
            }
            _ = tokio::time::sleep(std::time::Duration::from_secs(10)) => {
                if last_activity.elapsed() >= timeout_duration {
                    eprintln!("[SHADOW-NUDGE] Tool execution hung (>10m zero I/O). Aborting process...");
                    // Trigger interrupt event to LLM context
                    break;
                }
            }
        }
    }
}

## 1. Executive Summary
The **AGNOSTIC-HARVESTER** harness is a zero-cost, local pre-processing framework designed to convert raw user input into structured prompts for frontier-level LLM execution while preserving up to **85% of the model's context window**. It eliminates multi-turn chat loops, handles complex prompts with `/` or `.`, and resolves ambiguous terminology locally before invoking the model.

## 3. Detailed Module Breakdown
### Module 1: Local Zero-Cost Linguistic Engine (`Human Vibez`)
* **Ambiguous Term Resolver:** Uses a local dictionary of high-risk terms (`./harness/tools/ambiguous_terms.txt`). When an ambiguous term appears in the prompt, it logs the term and suggests alternative interpretations based on local definitions.
* **Grammar Normalizer:** Applies a simple grammar checker to identify common typographic errors (`//`, `;`, line breaks). The module then parses these into atomic tasks using local heuristic parsing rules.
* **Branching TUI (Terminal User Interface):** If ambiguity remains after resolution, the system presents interactive options to the user via a terminal menu. Options are selected by entering their index number (`1`, `2`, etc.). This avoids any additional token consumption during this step.
### Module 2: Prompt Splicing Manager
* **Sequential Task Decomposition:** Takes a single prompt and splits it into individual tasks only if no newlines or markdown headers exist. Each task is stored as a separate entry in the local dataset manager (`.jsonl`).
* **Prompt Assembly & Sequential Lock:** Ensures that each task must be completed and verified locally before proceeding to the next one. This prevents premature model invocation for incomplete subtasks.
### Module 3: Context Optimizer (AST Weaving)
* **AST Weaving & Pruning:** Scans the active workspace for boilerplate code, comments, whitespace, and irrelevant file references. It removes or summarizes these elements to keep the prompt concise and focused.
* **Dynamic Tool Headroom Expansion:** Creates a lightweight Python script (`./harness/tools/synthesized_tool.py`) dynamically when needed, saves its executable version to `.harness/tools/synthesized_tool_<id>.py`, and registers it in the MCP toolchain so that new tools can be added without breaking existing ones.
### Module 4: Error Recovery Loop (Reactive Hooks)
* **Catching Stderr Errors:** Intercepts all stderr output from model executions locally using CLI wrappers. If a tool fails, it runs a local generator to create a synthetic replacement script (`./harness/tools/<task_id>_synth_script.py`), verifies it locally, and adds it to the dynamic tool list.
* **No Token Cost Rejections:** All error handling actions use local scripts and do not require additional API calls or token costs. The goal is to achieve full model utilization with zero wasted tokens.
### Module 5: Shadow State Tracking (Git Delta)
* **Dataset Logging (`.jsonl`):** For every completed task, the system writes a JSONL record containing the task ID, prompt payload, execution trace, and verification results to `.harness/memory/dataset.jsonl`.
* **Shadow Git Delta Tracking:** Maintains a parallel git delta between the original project files and the generated outputs. If a code change is detected across multiple files, it creates diff entries for each affected file (`diff --name-only <file1> <file2>`), stores them in `.git/shadow-git/deltas/<project>/<day>`, and marks them as "modified" relative to the last commit date (`2025-04-08 15:47:15 -0900`).
### Module 6: Post-Processing Audit Loop
* **Comprehensive Audit Report:** Runs a suite of local tests (`linter`, `test runner`, `refactorization check`) over all modified files since the last commit. Outputs a comprehensive report showing what was changed, whether tests passed, and what was rolled back.
* **Interactive Recommendation Injection:** Presents a numbered list of suggested follow-up tasks (e.g., `[ ] Add unit tests for updated module`, `[ ] Refactor import statements`) to the user for immediate confirmation. Once confirmed, the changes are committed to the local repository.
